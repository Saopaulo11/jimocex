# Money write paths, and the precision PostgreSQL drops before a constraint sees it

Status: risk record. Describes the schema after migration 017.

## The risk

Every money column is `numeric(38,18)` (`fee_rules.percentage` is `numeric(10,6)`). When a value with more
fractional digits than the column's scale is written to the column, PostgreSQL rounds it — half away from
zero — while coercing it to the column type. That happens while the row is being formed, **before** any
CHECK constraint or trigger runs. Both only ever see the rounded value:

```sql
select '1.0000000000000000005'::numeric(38, 18)::text;   -- 1.000000000000000001
```

So no constraint, trigger or later query can tell that precision was lost, let alone restore it. The
database cannot refuse an over-precise value written straight into a column. The value has to be refused
**before** it reaches the column, by the code that sends it. `supabase/tests/01_invariants.sql` asserts
the rounding above, so a change in PostgreSQL's behaviour would show up. Measured on PostgreSQL 17: a
column with `CHECK (x = round(x, 18))` and `CHECK (scale(x) <= 18)` accepts `'1.0000000000000000005'`,
stores `1.000000000000000001`, and a BEFORE trigger on it already sees the rounded value.

The same applies to a value beyond the column's range: that is not rounded but refused (`22003`), so it
does not need a guard of its own.

## Who refuses it, per column

| Columns | Written by | Over-precision refused by |
|---|---|---|
| `wallets.available_balance`, `wallets.locked_balance` | `ledger_post()` only — INSERT/UPDATE/DELETE/TRUNCATE revoked from anon, authenticated, service_role (004, 017). The table owner is not restricted (see below) | `ledger_post()`: its parameters are unconstrained `numeric`, so it sees the original value and refuses `x <> round(x, 18)` with `22023` |
| `ledger_entries.amount`, `.available_delta`, `.locked_delta` | `ledger_post()` only — same revokes; UPDATE/DELETE also refused by `forbid_mutation` for every role, TRUNCATE by a statement trigger (both are triggers, which the table owner can disable) | `ledger_post()`, as above |
| `trading_orders.*`, `trades.*`, `swap_quotes.*`, `swap_orders.*`, `deposits.amount`, `withdrawals.amount`, `withdrawals.fee`, `limit_usage.usd_equivalent` | the server, as `service_role`, through PostgREST. anon and authenticated hold no INSERT/UPDATE/DELETE on any money table (checked by `scripts/check-money-catalog.ts`) | the application, before the value is `Money` (next section). `toDatabase()` (`src/lib/money.ts`), reached only through `moneyInsert` / `moneyUpdate` / `moneyArgs` (`src/lib/db/money-write.ts`), then refuses anything the column would alter: a value out of range, or more decimals than a narrower column holds (`fee_rules.percentage`). The `Database` type accepts only the `DbDecimal` brand that `toDatabase()` produces, and `scripts/money-guard.ts` fails the build on a money write that bypasses the helpers |
| `tier_limits.*`, `fee_rules.*`, `trading_pairs.*` | migrations (reference data); `service_role` could also write them, but the application only reads them | the person writing the migration — **no automatic guard** (a write through the helpers would be checked as above) |
| `trading_orders.remaining_amount`, `withdrawals.net_amount` | generated by PostgreSQL from the columns above; never written | not applicable |

## Where a decimal string becomes Money

`Money` holds at most 18 decimals by construction, so for a `numeric(38,18)` column a 19th decimal is
either refused or lost at the moment text becomes `Money`, not in `toDatabase()`:

| Entry point | A 19th decimal |
|---|---|
| `parseAmountInput()` — what a customer types | refused (`too_many_decimals`, against the asset's own decimals) |
| `fromDatabase()` — a value read back | refused (throws) |
| `parseMoney(text)` — any other decimal string | **truncated** to 18 places: its rounding mode defaults to `"truncate"`; a caller may pass another mode |

`parseMoney()` is used on external data in one place: the market-data price in
`src/lib/engines/limit-engine.ts` (`parseMoney(ticker.price)`). A provider price with more than 18
decimals would be truncated without notice before it values an operation against a limit. No provider
is connected (the engine answers UNAVAILABLE), so nothing reaches it today; before one is connected,
that call should refuse such a price, or round it in the direction a limit check needs.

## What remains unguarded

Any write that bypasses both `ledger_post()` and the typed server boundary is rounded silently:

- SQL run by the table owner (`postgres`): the SQL Editor, `psql`, a migration. This includes the
  reference data in `tier_limits`, `fee_rules` and `trading_pairs`. The owner is a separate trust
  boundary: it can also write `wallets` and `ledger_entries` directly and disable their triggers. Only
  review protects what it writes.
- Server code that ignores the types (`as never`, `any`) **and** escapes `money-guard`. The guard is a
  static check over the source, not a runtime one.

A database-side refusal would need the column itself to stop rounding: a domain over unconstrained
`numeric` with `CHECK (VALUE = round(VALUE, 18))`. That is not possible here without rebuilding tables:
`trading_orders.remaining_amount` and `withdrawals.net_amount` are generated from money columns, and
PostgreSQL will not change the type of a column a generated column depends on. It is recorded here
rather than attempted.

Operational rule until then: a hand-written SQL change to a money column uses a literal with at most 18
fractional digits (6 for `fee_rules.percentage`), and is reviewed as such.
